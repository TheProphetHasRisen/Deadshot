# Deadshot Record Book — working rules

Read `HANDOFF.md` for full project context. These are the operational rules for
every session in this repo.

## Build

```bash
python3 export.py     # data.py + weekly*.py  → site_data.json
python3 mksite.py     # site_data.json        → index.html AND sw.js
```

Both, in that order, after any source change. `mksite.py` prints the byte count.

## Never edit `index.html`, `404.html`, `sw.js` or `site_data.json`

They are build artifacts. `404.html` (the not-found page) is written by `mksite.py` from
`page/404.html` plus the six theme-token blocks it lifts out of `site.css`. `sw.js` (the offline copy that makes the site installable) is
written by `mksite.py` alongside `index.html`, and its version string is a hash of the
page — hand-edit it and the next build silently discards the change. `manifest.webmanifest`
sitting next to it *is* hand-written; that asymmetry is easy to trip over. Every change goes into `mksite.py` (the site) or
`data.py` / `weekly*.py` (the data), then you rebuild. Editing the artifacts
directly means your change is destroyed on the next build.

## Where the page lives

`mksite.py` is now an 84-line assembler. The page itself is in `page/`, as real files
an editor and a linter can read:

| File | What |
|---|---|
| `page/shell.html` | doctype, `<html>`, meta tags |
| `page/head.html` | `<title>` and the `__CSS__` placeholder |
| `page/fonts.css` | the six `@font-face` rules — **generated** by `mkfonts.py`, never hand-edited |
| `fonts/` | the six `.woff2` files and their OFL licences, self-hosted since 25 Sep 2026; also generated by `mkfonts.py` |
| `page/site.css` | ~97 KB — every rule for all six themes |
| `page/body.html` | the markup, and the `__DATA__` placeholder |
| `page/scripts.html` | the `<script>` wrapper, and the `__JS__` placeholder |
| `page/site.js` | ~280 KB — the whole page's behaviour |
| `page/ask.js` | "Ask the record book", the plain-English search. Appended to `site.js` inside the same `<script>`, so it reads the page's globals directly; `eslint.config.js` lists the ones it uses |
| `page/sw.js` | the offline worker, with `__VERSION__`; its `CORE` list names the six font files |
| `page/404.html` | the not-found page, with `__TOKENS__`. Standalone: it does **not** load `site.css`, only the theme tokens, so it has its own small `.nf-*` stylesheet inline |

Until 14 Sep 2026 all of that was five giant raw strings inside `mksite.py`, which was
6,664 lines. Editing CSS inside a Python string meant no highlighting, no autocomplete
and nothing a linter could read. The split was verified byte-identical: same page, same
worker, to the byte.

**`page/site.js` is ~280 KB / ~4,600 lines — do not read it in full.** It will consume
most of the context window in one call. `grep -n` for the anchor, then read a narrow
window (`sed -n 'START,ENDp'`, or `Read` with `offset`/`limit`). Line numbers move as
you edit, so re-grep rather than trusting a remembered offset. Prefer targeted `Edit`
calls over rewriting regions.

`page/site.css` is one block shared by six themes — see the CSS-collision rule below.

If you patch with a Python script instead of `Edit`, **assert every anchor
matches exactly once before opening the file for write**, and `grep` afterwards
to confirm the change landed. A script that throws mid-way after making earlier
in-memory edits silently discards all of them. This has cost real work more than
once.

## Never type a season count, manager count or game count into the copy

"ten seasons", "twenty managers", "410 games logged", "all 55 playoff games" were typed
by hand into the page copy, the meta tags, the manifest and the link-preview cards. Every
one of them would have started lying the day 2026 landed. They are computed now:

- In `BODY`, `HEAD` and `SHELL_TOP` (and in a JS string where the copy needs a *word*
  rather than a digit), write a placeholder: `__NSEASONS__` / `__NSEASONSW__` ("ten") /
  `__NSEASONSWC__` ("Ten") / `__FIRSTYEAR__` / `__LASTYEAR__` / `__NMGRS__` /
  `__NMGRSW__` / `__NTEAMSZN__` / `__NLOGGED__`. `mksite.py` fills them from
  `site_data.json` at build time and **asserts that none survive**, so a typo fails the
  build instead of shipping `__NSEASONSW__` in the middle of a sentence.
- In JS where a digit is fine, read it live: `SEA.length`, `D.games.length`, `M.length`.
- `mkog.js` reads the four masthead figures off the built page, so the preview card, its
  alt text and all six `t/*.html` shims follow on their own.
- `manifest.webmanifest` is still hand-written, so its description deliberately carries
  no count at all ("Every season of...").

To check a change here, clone the newest season as a fake next year in a scratch copy,
rebuild, and confirm the wording moves to "eleven".

## Before introducing any new CSS class or `@keyframes` name

`grep` for it first. The stylesheet is one giant block shared by six themes, and
collisions are silent:

- a new `.brand` inherited the masthead's `.brand` and broke the layout
- a new `.totop.on` inherited the global `button.on` and inverted its colors
- `sweep` was defined twice as a keyframe and the wrong one won

Never hardcode a color. Use the CSS custom properties (`--brass`, `--surface`,
`--ink`, `--pos`, `--neg`, …) — all six themes have to survive every change.

## Verify before you report done

1. `python3 export.py && python3 mksite.py`
2. `npm run lint` — eslint over `page/site.js` and `page/sw.js`. Bugs only, no style
   rules. It must come back **completely silent**; warnings that live forever get
   ignored, so fix them or justify them with a commented `eslint-disable-next-line`.
   `node --check` only answers "does it parse" and misses a typo'd name entirely.
3. `node test.js` (set `CHROMIUM_PATH` if Playwright can't find a browser).
   `net::ERR_TUNNEL_CONNECTION_FAILED` is expected sandbox noise, not a failure.
4. For anything visual, drive it in a headless browser and screenshot it. Check
   the change in more than one theme when it touches CSS.
5. For anything that has to work on a phone, test in **WebKit** (Safari's own engine)
   at iPhone sizes, not just Chromium. `node test.js` now does a WebKit pass at
   `devices['iPhone SE']` / `devices['iPhone 15 Pro']` automatically (no page errors, no
   sideways page scroll, the typefaces load, the dossier opens and closes), and
   `deploy.sh` will not push without it -- if it prints "WEBKIT NOT INSTALLED", run
   `npx playwright install webkit` once. For anything visual beyond those checks, drive
   WebKit yourself the same way and screenshot it. The SE is 320pt and finds the layout
   breaks nothing else does.
   There is **no Xcode on this Mac and Brian has decided not to install it** (Sep 2026 —
   a ~15 GB download whose only benefit here is the Simulator). Do not suggest it again;
   the iOS Simulator tools will fail, and WebKit is the substitute.

6. `python3 test_copy.py` after touching any wording. It fails on an em dash in the writing
   (see "House style" below). `deploy.sh` gates on it.

7. `node test_ask.js` after touching the search, the data, or any helper it uses. 65 questions,
   typos and slang included, each checked against numbers worked out independently from the
   data, then the box driven with the keyboard and on an iPhone SE. `deploy.sh` gates on it.

8. `node test_rules.js` after touching the League rules card. It asserts all 35 of
   Yahoo's scoring categories are present in BOTH places the rules are drawn, and that
   the six non-default values still carry their "(default N)" note. A category dropped
   from that card is invisible by eye -- the card still looks complete.

9. `python3 test_wire.py` after touching the 2026 trades, moves or `wire2026.py`. It recomputes every
   trade grade (each player before and since, against his own form, both teams' records, all-play
   and wins against pace) and the top pickups from the raw moves, without importing `wire2026.py`.
   `deploy.sh` gates on it.

Do not report a fix as working on the strength of the code reading correctly.

## House style: the words and the numbers

Brian asked (12 Oct 2026) for everything on the page to look like time was spent on it. The
pass that followed found that the big things already did and the small things did not. These
are the rules that came out of it. Most are enforced; all of them are easy to undo by accident.

**No em dashes in the writing.** Not in a sentence, a heading, a label, a tooltip, a share
card or the link-preview text. He had them all removed once (Sep 2026) and about 85 crept
back, nearly all in copy written afterwards. Use a full stop, a colon, a comma, brackets or
`&middot;`. The lone `—` that marks an empty table cell is fine. `test_copy.py` enforces this.

**Numbers go through the helpers at the top of `page/site.js`, never a bare `toFixed`:**

| Helper | Gives | Instead of |
|---|---|---|
| `sg(v,d,suffix)` | `+1.23`, `−1.23`, `0.00` — a real minus (U+2212), a plus on a gain, no sign on zero | `(v>=0?'+':'')+v.toFixed(d)`, which prints `+0.00` and a hyphen |
| `ty(html)` / `tyMinus(html)` | fixes a string that is already formatted: real minus, and `9–5` for a record. Text nodes only, never an attribute | hand-editing each cell. `table()` runs `ty` on every `c:'num'` cell and `showTip` runs `tyMinus` |
| `nOf(n,'season')` | `1 season`, `2 seasons` | `n+' seasons'` |
| `yearList(a)` / `yearSpan(a)` | `2021–2025`, or `2021, 2023 and 2025` | `a.join(' and ')` |
| `ord(n)` | `21st`, `11th` | the old one-liner, which printed `21th` |

A win-loss record is written with an **en dash** (`${w}–${l}`), everywhere. Luck is a
**signed** quantity in every table. Team names are data and are never touched: `ty` is built
so `“Close”~~~ 0.33-0.42` survives, and the curly-apostrophe pass skipped all twelve team
names that contain one.

**No stock browser furniture.** Selection colour, dropdown arrows, scrollbars, the text
cursor, the search box and list bullets are all restyled from the theme tokens (search
`the browser's own furniture` in `site.css`). Three traps:

- Do **not** add `::-webkit-scrollbar`. Defining it makes Safari on a Mac swap its overlay
  scrollbars for permanent ones and every table card grows a bar. Standard
  `scrollbar-width` / `scrollbar-color` only.
- `select` uses `appearance:none` with the arrow drawn as a `background-image`. A later
  `background:` shorthand on a select would erase the arrow and leave nothing. Set
  `background-color` instead.
- No regex lookbehind in `site.js`. Safari before 16.4 cannot parse one, and a parse error
  kills the whole page, not one feature.

**A `title=""` attribute becomes the site's own tooltip automatically** (delegated from the
document, so it covers markup drawn later). Just write `title="..."`; do not also `bindTip`.

**A table with no rows explains itself.** `fillEmpty(tableEl)` runs after every draw; call it
after any new hand-built table's `innerHTML`.

**Never type a colour into `page/404.html` either.** It reads the same tokens as the masthead.

## Ask the record book (the search)

Brian asked (14 Oct 2026) for the Celtics Hub's search on this site: intuitive, live as you
type, forgiving of typos and of how people actually talk. It is `page/ask.js`.

- **It reads, it does not compute anything new.** Every answer comes from the same rows,
  career figures and head-to-head tallies the page shows (`ROWS`, `M`, `MX`, `REGG`, `POG`).
  A question it cannot answer says so; it never estimates.
- **Typos**: a word it does not know is swapped for the nearest known word (names, team
  names, players, measures, ordinary question words), and the answer says "Read X as Y".
  A name two slips away must keep its first letter. Ties go to a manager, then a measure.
- **How people talk**: the `SAY` list rewrites "goat", "who owns Kaiper", "choker",
  "robbed", "fraud", "smashed" and so on into the plain question. Add to it there.
- **Ambiguous names ask**: "Brian" and "Watson" are two managers each.
- **The game log (`games1()`) is the second layer.** One row per team per game: every
  regular-season game in the logged seasons (both scores, both Yahoo projections, that week's
  all-play count) and every playoff game. A question with a *slice* goes there: week ranges
  ("weeks 1-4", "first 4 weeks", "last 3 weeks", "second half", "after week 8"), situations
  ("close games", "blowouts", "scoring 150+", "under 100", "allowing over 140"), projections
  ("as an underdog", "favorite", "beat the projection", "points vs projection", "biggest
  upset"), opponents ("against winning teams", "playoff teams"), sequence ("after a loss"),
  result ("in wins") and splits ("by week", "by season"). Slices stack (all conditions must
  hold) and work for one manager, a pair, or a leader board, and with "how many / how often"
  as counts. A one-manager answer always shows the layer underneath: the same seasons with the
  slice taken out, and the league rank in the slice (4+ games). Week-based and projection
  questions mean the regular season unless playoffs are named; the rest use every game.
- **The third layer is the detail under every answer**: a career gets "Inside the numbers"
  (best and worst season, highest and lowest score, weekly highs and lows, streaks, nemesis,
  favorite opponent, trades, team names); a head to head gets "Inside the matchup" (each
  side's scoring, biggest wins, closest game, playoffs apart, current run, by season); a
  season gets its one-game records. Other kinds of question: streaks, "who has never beaten
  X" / "who has X never beaten", "who does X own", seeds ("how often does the 1 seed win",
  "every seed"), "does the best team win", team names, one manager's trades, weekly high and
  low scores, bad beats (lost while outscoring half the league) and lucky wins.
- **Typo repair never rewrites a word the patterns use**: the vocabulary is filled from
  `parse`'s own source, so a new pattern word is protected automatically.
- **Who won a trade** needs each player's points before and after; it is answered with what
  is coming until `D.playerStats` exists. That is the natural next layer once Yahoo lands.
- **Adding a slice** is three edits: the phrase in `parse` (the block above `/* weeks */`),
  the test in `inSlice`, the words in `sliceLine`. Then a case in `test_ask.js` whose answer is
  computed from its own independent game log, not from ask.js.
- **When the Yahoo data lands**, three places change: put player names in `D.players` (the
  dictionary picks them up), write the answerer for the new data (drafts, injuries, waivers,
  lineups), and its `SOON` line stops showing on its own once `D.draft` / `D.injuries` /
  `D.waivers` / `D.lineups` / `D.playerStats` exists. Add the new questions to `test_ask.js`
  with independently computed answers.
- No Claude/API translator on purpose: it would need a paid API key in a page the whole
  league opens. That is Brian's call (it costs money), not a technical one.

## The live season (2026)

**Yahoo is connected (15 Oct 2026).** Each week, after the games:

```bash
python3 yahoo_fetch.py 2026      # raw replies into yahoo_raw/2026 (gitignored cache); --extras = schedule + rankings only
python3 yahoo_to_2026.py         # -> season2026_yahoo.py (generated, committed)
python3 draft_points.py          # re-score every player from Sleeper for ranks and pools
python3 export.py && python3 mksite.py
```

`season2026.py` imports `season2026_yahoo.py` at its bottom, so Yahoo's scores, projections,
standings, moves, trades (with exact times) and weekly rosters replace the typed copy wherever
Yahoo has them; the typed lists stay as the fallback, along with the two drafts and the contested
waiver claims (not in Yahoo's API). Every typed game, pick, add, drop and trade matched Yahoo.
Times are US Eastern; a move counts from the first Sunday 1:00 pm Eastern kickoff after it.
`teamfile.py` builds the 2026 **team files** (each manager against the league and his own
2021-2025: lineup efficiency by brute-checked best lineups, pickups over the bench, patience,
drops that came back, draft, trades, wins above average) and the **playoff odds** (a regression of
rest-of-season scoring on early scoring over 2021-2025, then 20,000 simulated finishes of the
real schedule). It reads yahoo_raw/2021-2026, so on a fresh machine pull every season first
(`for y in 2021 2022 2023 2024 2025 2026; do python3 yahoo_fetch.py $y; done`, ~1,200 calls).
`test_teamfile.py` checks it and `deploy.sh` gates on it.
`ROSTERS2026` (who started each week, Yahoo's official points) drives the trade cards'
"Started" column and "Points that counted" tile. Yahoo reaches the league for 2021-2026 on
Brian's account; 2015-2020 are not listed there.

`season2026.py` holds the live season as typed from Brian's screenshots (now overridden by Yahoo, above);
`check_2026.py` reconciles it (records, streaks, PF, PA, both drafts as snake orders).
`export.py` writes it as `D.live`, kept OUT of rows/careers-by-season/champions, but its
games DO count in head to head, career W-L/PF/PA/PPG/all-play and the search's game log.
`draft_points.py` scores every drafted player from Sleeper's public weekly stats with the
league's own scoring and writes `draft_points.json` (re-run it weekly in season); the draft
board's steals, busts and best drafts come from that.

## The numbers tripwire

`python3 test_numbers.py` pins every computed number -- power index, Z, pythagorean
wins, luck, all-play, expected titles -- for all 96 team-seasons and the 10 retired
managers' careers. `deploy.sh` gates on it.

It exists because **a changed formula has no symptom.** Proven, not assumed: changing
the pythagorean exponent from 2.37 to 2.38 moves 252 numbers and `verify.py`'s 7,470
checks still pass with exit 0. The page renders, nothing looks wrong, and the site shows
confident wrong numbers. That is the one failure mode nothing else here catches.

- **It stays quiet when a season is added.** Team-seasons are frozen history; careers are
  pinned only for managers who have stopped playing, because an active manager's career
  numbers rightly move every September. A test that cries wolf every season gets
  `--accept`ed without reading, which is worse than no test.
- **When it fails, read what moved.** Changed something on purpose? `python3
  test_numbers.py --accept` and commit `numbers.lock.json` in the same commit as the
  change, so the diff shows both. Didn't change anything on purpose? A formula is broken.
- It is deliberately blind to raw-data errors -- a mistyped score is `verify.py`'s job.

## Data changes

Run `python3 verify.py` after any data change. It automates the invariants below and
exits non-zero if any fail. `writer.py` runs it before writing and refuses to write
anything that does not pass, so a bad fetch is a no-op rather than a broken site.
Finished seasons are frozen: only the season named as live may be rewritten.

The invariants it enforces — they have caught real transcription errors:

- league-wide PF equals PA to the cent
- every team's W + L + T equals the season length
- total W equals total L
- the weekly game log reconciles against `STANDINGS`

### A rebuild that changes only pythW / luck / expOverAvg is expected

These three come from `pf**K/(pf**K+pa**K)` with `K = 2.37`. The fractional exponent
lands in the platform's libm `pow()`, so the last 1-2 bits vary between machines.
`index.html` and `site_data.json` are therefore **not** bit-reproducible across
machines, and a rebuild moving only those fields in the embedded JSON is not a
regression — do not "fix" it or treat it as a failed build.

It is not a Python version or CPU architecture difference; those were tested and
agree. Verify the claim structurally (parse and compare values) rather than by hash:
changed key order, thousands of differing values, or any non-float field moving means
something is actually wrong.

## Layout traps this codebase has actually hit

Grep before you add, and check the fix on a phone as well as a desktop.

- **`position:fixed` + `left:50%` with no width** shrink-to-fit caps at *half the
  viewport*. `.toast` was 195px on a 390px phone. Set `width:max-content` and a
  `max-width`.
- **`preserveAspectRatio="none"`** stretches text as well as shapes. The redacted
  dossier was scaled 7.2:1 on a phone. Bars survive it; type does not — keep text out
  of a non-uniformly scaled SVG, or make it real HTML.
- **`th,td{white-space:nowrap}` is global.** Long content pushes the right-hand column
  out of any `.scroll` card. Let a text column wrap instead of adding more scrolling.
- **A sticky element inside a horizontal scroller** needs its own opaque backdrop, and
  must be checked against whatever else is absolutely positioned there — the nav's
  `.navmark`, its scroll arrow and its fade gradient all wanted the same 46px.
- **`--nav-bg` and friends are translucent** (94-96%). Layering the token twice gets to
  ~99.6% without hardcoding a colour.
- **A long team name with no spaces cannot wrap.** Trade cards are titled
  "TeamA <-> TeamB" with a two-column body; a 40-character unbroken name pushed both out
  of the card on a phone. A plain `1fr` grid column will not shrink below its longest
  word — `minmax(0,1fr)` will. Fixed with that plus `overflow-wrap:anywhere` on
  `#trades .card-h h3` and `#trades .sub-h`. Names with quotes, ampersands, raw HTML,
  emoji and Arabic were all stress-tested: they render as text and nothing injects.
- **`data-m` is the manager-link attribute** and a global handler turns any click on one
  into `openMgr()`. Four Season Shape buttons already overload it as a metric key. Use a
  different attribute for new controls.

## Deploy

Use `./deploy.sh` (build + verify only) and `./deploy.sh --push` with
`DEADSHOT_REPO=TheProphetHasRisen/Deadshot` to ship. It verifies before it pushes and
commits `index.html` to `main` in one commit. Auth is `gh`, token in the macOS keyring —
**never ask for or accept a personal access token.** Vercel deploys straight from it.

**No need to ask before pushing** (Brian, 2026-09-12 — this replaces the earlier "confirm
before every push" rule). Finish the work, let `deploy.sh` run its checks, and ship it.
The gate is what makes that safe: `deploy.sh` refuses to push if the page's JavaScript
does not parse, if `test.js` finds an error, if the worker or the manifest is broken, or
if Playwright is missing. Do not push around it, and do not push work that is half-done
or that he has not asked for — say what went live afterwards.

Manual drag-and-drop still works but Chrome renames to `index_NN.html`, which cost three
commits per deploy and a 404 once. If you do it by hand the filename must end up exactly
`index.html` and the old file is never deleted first.

## Who you are talking to

Brian owns this league and built this site with AI help. **He is not an engineer.**
Write every word to him on that basis.

### Reporting what you did

- Lead with **what changed and whether it worked**, in plain English.
- **No file paths, line numbers, or function names** unless he asks for them.
- **Never assume he knows a term.** Say "the thing that builds the page", not
  "the generator". Not "the DOM", "the build artifact", "the schema", "z-index".
  If a technical word is genuinely unavoidable, define it in the same breath.

  "the standings table is blank on phones" beats "the grid template is wrong".

  not need to see how the sausage was made to trust that it works.

### Decisions

**You make the technical calls. He does not want to be asked.** Which library,
which approach, how to structure something, what to name things, how to fix a bug —
pick the best option and say what you picked in one line. Asking him to choose
between technical options is offloading your job onto him.

Bring him a decision only when it is genuinely his:

- how the site should look or feel
- what to build next
- anything that costs money
- anything that cannot be undone

### When he has to do something himself

Walk him through it exactly, assuming he has never done it before. Every click,
every screen, what to type, and **what he should see when it worked**. Name the
application to open and quote the exact text to paste.

Not "authenticate with gh". Instead: open Terminal, paste this line, press Enter,
you'll see a screen asking X, choose Y, a browser tab opens, click Z, and when it
